# Decision: 适配 DSH 0.1.7 的任务与配置接口

Status: implemented

## Problem

环境事实：DSH 0.1.7-rc.2 的 jobs 服务没有 `onJobDone`，`list` 接收会话 ID；旧前端依赖 `settingsScope` 会阻止插件挂载。settings 服务也不提供旧 `register` 方法。原有插件会加载失败，或失去配置写入入口。

## Decision

使用 `jobs.events.subscribe({ owners: 'scope' }, listener)`，只消费 `settled` 事件的 `job`；成功、失败和取消的账本语义不变，订阅随插件卸载清理。任务枚举传入 `agent.id`。

Node half 导出宿主版本的 Schemastery `Config`，通过 volatile 引用读取实时配置，沿用只读 `/config` 和 `/state` 的 revision 协议。客户端不注册旧设置卡片，也不等待已移除的设置服务。旧 settings.yaml 不自动迁移；原生表单在 bundle 下的可见性与保存流程仍需端到端确认，不能视为已经恢复完整设置体验。

构建器通过 Node 启动本地 esbuild JS CLI，使 Windows 能运行同一生成和新鲜度检查流程；缺少本地包时保留原候选路径。

## 取代检查

部分取代 [config-system](../feature/2026-08-09-config-system.md) 的宿主注册方式；保留只读路由、体验层范围和账本边界。
部分取代 [settings-card](../feature/2026-08-31-settings-panel-card.md) 的客户端挂载方式；旧卡片源码保留用于后续迁移参考，当前客户端不加载它。

## Alternatives considered

仅修复 `onJobDone`：前端仍等待不存在的服务，不能恢复宠物显示，因此同时移除客户端的旧服务硬依赖。

将本机修复目录和宠物存档直接发布：本机专用路径与数据不适用于其他用户，因此本改动保留上游存储路径规则，不包含存档和本机配置。

## Consequences

目标宿主为 DSH 0.1.7-rc.2；更早版本及 0.2 系列未经验证。`tests/host-compat.test.mjs` 使用该版本公开接口形状的替身验证任务终态、取消中性、轮询不重复加 XP、配置 revision、卸载和存档重载，不替代真实任务与原生设置 UI 的端到端测试。PR 保持草稿，设置 UI 验证是转为可合并状态前的待办。
